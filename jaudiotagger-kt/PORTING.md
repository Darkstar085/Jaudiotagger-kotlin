# jaudiotagger-kt — Kotlin Multiplatform port

Incremental port of jaudiotagger (Java, `../src`) to Kotlin Multiplatform.

## Porting rules

1. **KMP-first**: all logic lives in `commonMain`. Platform specifics go through
   `expect`/`actual` (`FileIo`) or interfaces. Compiling `macosArm64` verifies
   the common code stays JVM-free (linking/running native tests requires a full
   Xcode install).
2. **No reflection**: the ID3 frame body factory (`Class.forName("FrameBody"+id)`
   in `AbstractID3v2Frame`), frame copying (`ID3Tags.copyObject`) and ASF reader
   registration (`ChunkContainerReader.registerChunkReader`) are replaced with
   explicit `when`/`Map<String, () -> T>` factories. R8/ProGuard must be able to
   shrink the library without keep rules.
3. **All I/O goes through `FileIo`** (`io/FileIo.kt`): positioned reads/writes
   plus truncate. Path-based functions are a thin convenience layer. This lets
   Android callers edit MediaStore/SAF files through a `FileDescriptor` without
   temp copies (`FileDescriptorIo` over `Os.pread/pwrite/ftruncate`).
4. **Idiomatic API, 1:1 parser/writer logic**: readers and writers are ported
   faithfully, including known quirks (e.g. integer division in the FLAC bitrate
   computation), so behaviour matches the old library on the same files.
5. **Tests run against real files** from `../testdata`; expected values come from
   the original JUnit tests in `../srctest`. Mechanical tables (field enums,
   mappings) are generated by script from the Java sources, never retyped.
6. Logging: none for now (java.util.logging dropped). If needed later — a small
   pluggable callback, no dependencies.

## Recommended order

**The port is complete**: all 13 formats (FLAC, Ogg Vorbis, Ogg Opus, APE, WavPack,
Real, MP3, DSF, DFF, WAV, AIFF, MP4, WMA), Android/iOS/macOS/JVM targets, publishing.
Possible follow-ups: cross-validate behaviour against the Java library over a
large real-world collection, integrate into the player app, add a
`SamplesSmokeTest`-style corpus runner for regression hunting.

## Fixed porting bugs

- **ShiftData shrink truncate (round 7):** `shiftDataByOffsetToShrinkSpace` called
  `truncate(io.position)` when nothing followed the start position, leaving stale
  bytes at the end of the file after a shrunk last-atom write.
- **ID3v2 zero-size frames (round 5):** `Id3v2TagReader` stopped the frame loop on
  `declaredSize <= 0`, so a leading or mid-tag empty frame (e.g. v2.3 `WOAF`, v2.4
  `TYER`) hid all following metadata. Now matches Java's `EmptyFrameException`
  handling: consume the frame header and continue.
- **MPEG-2/2.5 Layer III duration (round 5/6):** `MpegFrameHeader.noOfSamples` used
  1152 for every Layer III frame; MPEG-2/2.5 Layer III carries 576 samples per
  frame per ISO/IEC 13818-3. Fixed via a version/layer sample map; MPEG-2/2.5 Layer II
  mono still halves time-per-frame as in Java.
- **MPEG-2/2.5 Layer III frame length (round 8):** `MpegFrameHeader.frameLength`
  used `144 ×` for non-mono MPEG-2/2.5 Layer III (ported from Java), breaking sync
  confirmation and halving Xing-count-0 duration estimates for stereo files. Fixed to
  `72 ×` for every channel mode; the round-6 CBR-only `mpeg2Layer3SlotLengthForCount`
  workaround was removed.
- **ASF/WMA container write (round 3):** replaced the round-2 dedupe/strip workaround
  with Java's container model. Read keeps every descriptor in `ContainerType` order;
  write runs `distributeMetadata` so each descriptor lands in the first container
  that accepts it (large `WM/Picture` → Metadata Library, duplicate names across
  containers preserved on read, ECD preferred for `first()`).


- **ID3v2 TRCK/TPOS (TRK/TPA in v2.2):** the mechanical port treated track/disc
  number frames as plain text, so `first(TRACK)` on `"3/12"` returned the whole
  string and `set(TRACK, "5")` dropped the total. Fixed by porting
  `AbstractFrameBodyNumberTotal` / `deleteNumberTotalFrame` behaviour. The same
  partial-delete semantics were applied to MP4 `trkn`/`disk` atoms (removing
  `TRACK` zeroes the number but keeps `TRACK_TOTAL` when present).
- **MP4 genre:** `Mp4TagReader` converted every `gnre` atom into a `©gen` text
  item, so `first(GENRE)` was always null and `set(GENRE, …)` wrote malformed
  text into `gnre`. Fixed by porting `Mp4GenreField` / `Mp4Tag.createGenreField`
  (separate `gnre` uint16 and `©gen` text atoms).

## Known intentional deviations from the Java library

- **MP4 write layout (round 7):** the kt MP4 writer works in place and leaves
  `free` padding after `moov` so later edits avoid shifting the whole file.
  File layout and size after a write differ from Java; tag values are identical.
- **MPEG-2/2.5 Layer III frame length (round 8):** Java's
  `MPEGFrameHeader.getFrameLength` uses `144 × bitrate / sampleRate` for non-mono
  MPEG-2/2.5 Layer III, so its sync checks and Xing-count-0 estimates are off for those
  files. kt uses `72 ×` per ISO/IEC 13818-3 for every channel mode. Durations and the
  frame chain are verified against ffprobe/afinfo and a walk to EOF.
- **MPEG-2/2.5 Layer III samples per frame (round 5/6):** Java's `noOfSamples` gives
  1152 for MPEG-2/2.5 Layer III stereo; kt uses 576 per ISO/IEC 13818-3 for every channel
  mode, matching `afinfo`/`ffprobe` ground truth.
- **Xing/VBRI frame count zero (round 5):** when a Xing/Info or VBRI header advertises
  a frame count of 0, Java's `MP3AudioHeader.setNumberOfFrames` keeps 0 and the
  duration collapses. kt scans past the VBR wrapper slot for the first MPEG frame
  whose successor matches its own header (skipping transitional bitrates), then
  estimates `(audio end − that frame's start) / that frame's length`.
- **Vorbis `ALBUM_ARTIST` write/remove:** on `set(ALBUM_ARTIST, …)` kt writes
  `ALBUMARTIST` and deletes JRiver's `ALBUM ARTIST`; on `remove` both are
  deleted. Java's default `WRITE_ALBUMARTIST` would leave a stale JRiver field.
  Read still follows Java's `READ_ALBUMARTIST_THEN_JRIVER` fallback.
- **ID3v2 `COMMENT` / `LYRICS`:** user comment frames exclude `COMM`/`COM`
  whose description starts with `iTun` (iTunes internal frames). Empty-
  description frames are preferred for `first()` and listed first in `all()`.
  Java returns every `COMM`/`USLT` regardless of description.
- Vorbis comment names keep the spelling from the file (lookups stay
  case-insensitive). Java uppercases them, which would rewrite every
  ffmpeg Opus tag on a no-op write.
- Ogg (Vorbis and Opus) writing is in-place instead of temp-file based
  (MediaStore requirement).
- **Vorbis combined TRACKNUMBER/DISCNUMBER (round 10):** a value matching
  `N/M` is split into number and total for `TRACK`/`TRACK_TOTAL` and
  `DISC_NO`/`DISC_TOTAL`; `set`/`remove` keep the total. Java returns the
  raw `3/12` string.
- **Ogg Opus (round 9):** the Kaned1as fork was the format reference but was not
  ported. That writer loads the whole file into memory, rewrites through a temp
  file, and drops data after the comment list.
- `readSetupHeaderAndExtraPackets` detects the setup packet position by
  signature; the Java version mis-detected it when the comment ended exactly
  at a page boundary and threw.
- Corrupt samples `test36.ogg`, `test508.ogg` fail with `CannotReadException`
  exactly like the original (covered by `SamplesSmokeTest`).
- Monkey's Audio: the fork's Java reader parsed the APE_HEADER with two uint32
  fields at the front (spec says uint16 compressionLevel + uint16 formatFlags),
  so every offset was shifted and `test000*.ape` failed to read. Ported per
  spec; both samples read and cross-check against their WavPack twins.
- APEv2: the fork mis-derived the item start when the tag has a header
  (`tagStart + 32`), so it could not read back tags it had written. Fixed per
  spec (footer size covers items + footer, never the header).

## Building

The Gradle build lives at the repository root (required for JitPack):

```bash
./gradlew :jaudiotagger-kt:jvmTest                  # compile + run tests on JVM
./gradlew :jaudiotagger-kt:compileKotlinMacosArm64  # verify common code is KMP-clean
./gradlew :jaudiotagger-kt:assembleRelease          # Android AAR
```

Tests read audio samples from `testdata/` (path is passed via the
`TESTDATA_DIR` env var by the build script). JitPack builds are configured in
the root `jitpack.yml` (android + jvm + KMP metadata; Apple targets need a
macOS host).
